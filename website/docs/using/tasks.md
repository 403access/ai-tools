# Tasks

The **Tasks** tab is the default view. It is a project-management board built
from sessions: every new top-level session becomes a task.

## Board columns

| Column | What it means |
| --- | --- |
| **Queued** | Waiting for a start time or a free concurrent-agent slot |
| **Needs review** | Finished, stopped, or failed work waiting for you |
| **In progress** | Running now |
| **Done** | Accepted work, hidden until you show completed tasks |
| **Dismissed** | Work you removed from the board |

Each card shows the task title, project, status, labels, and the last activity.
Open a card for the full [session view](session.md), or use the card actions to
start a queued task, mark it done, reopen it, or remove it from the queue.

## Filters and grouping

Both apps filter the board by **project**, **date** (all time, today, last 7
days, or last 30 days), and **outcome** (finished, failed, or interrupted).
These filters sit behind the funnel icon in the Tasks header. The icon opens a
drawer with project, date, and outcome, and shows how many filters are active.
The status chips remain in the tab and switch between queued, review, in
progress, done, and every task.

Date and project is the default grouping in both apps.

- On iOS, the filter drawer's **Grouping** section offers None, project, date,
  or date and project. Date grouping can bucket by day, week, or month, and
  applies to both the portrait list and the landscape kanban columns.
- On macOS, **Group** splits each status column by project, by date (day, week,
  or month), or by date and then project. The compact panel and a narrow split
  column use the same grouping for their single-column list.

Project group headers use the project's own app icon when the hub finds artwork
for it, and fall back to the folder symbol otherwise. Switch this off in
**Settings → App → Project icons in Tasks** on macOS or
**Settings → Appearance** on iOS.

The empty state suggests another project, date range, or status when no tasks
match.

## Running work

Session activity still updates in real time from OpenCode's event stream.
Running tasks show their status on the board, and the session header and Home
Screen widgets show the current tool, reasoning or text, todo progress,
subagent count, live cost, and tokens. Cost and tokens move as usage events
arrive instead of waiting for the next poll.

## Start a new session

Use **New task** on the Tasks tab (or the plus button on a project page):

1. Pick a project from the searchable browser — sort by recent, name, or running
   work, and filter to running, Git, or sandboxed projects — or type a custom
   path.
2. Optionally give the session a title.
3. Optionally type or dictate a first message.
4. Create the session.

The new session opens immediately, and the first message is sent in the same
step. You can fix a failed first message and retry without creating a second
session.

### Choose where the session works

For an existing folder, **Workspace** decides where changes land:

- **Current folder** edits the selected checkout in place.
- **Git worktree** asks OpenCode to create an isolated checkout with the
  project's configured worktree strategy, runs its setup script, and starts the
  session there. The worktree name and location are generated by OpenCode, so
  parallel sessions do not fight over the same files.

Worktrees are available when the selected project is a known Git project. A
custom folder path or a repository you are about to clone starts in place.

### Clone a repository

Switch the source to **Clone repository** to start in a project that does not
exist yet. The hub runs `git clone` on the Mac, so the folder is ready before
the session starts.

- Paste an HTTPS, SSH, `git://`, or `file://` URL, an scp-style SSH remote, or
  GitHub `owner/repo` shorthand.
- Choose the parent folder (defaults to `~/Developer`) and, optionally, a
  folder name. The repository name is used when the name is blank.
- **Clone & create** clones the repository and starts the session in it.

The clone refuses to write over an existing folder. Private repositories use the
git credentials and SSH agent already configured on the hub host; git never
prompts for a password, so an unauthenticated private clone fails with git's
error instead of hanging.

:::note
The apps can start sessions and send prompts, pause or stop a session, and
continue held work. Neither app deletes sessions. Prompts sent to a running
session are queued behind the current turn; the queue is listed above the
composer, where a prompt can be withdrawn before the turn starts it.
:::

## Menu bar count

On macOS the menu bar item shows the number of active sessions while work is
running. Click it to open the panel; the live state stays current while the
popover is open.

See [Session detail](session.md) for the conversation, stats, changes, prompts,
and subagents.
